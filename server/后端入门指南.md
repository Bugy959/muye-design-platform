> 写给新手：这是一份逐文件的功能讲解，不需要有后端基础也能读懂。
> 如果你想知道"这个文件是干嘛的"或"为什么这样写"，从这里开始。

## 一、整体架构（先搞清楚谁是谁）

```
浏览器（前端）  ──HTTP请求──→  后端（server/）  ──读/写──→  数据库（muye.db）
     ↑                              ↑
  你做的网站                    这 5 个文件
```

**前端** = 用户看到的界面（`website/` 目录，你已经很熟了）

**后端** = 藏在服务器上的程序，负责存数据、验证身份、算积分。不直接给用户看。

**数据库** = 一个文件 `muye.db`，相当于一个超级大 Excel，所有数据都在里面。

**一次"下单"发生了什么：**
1. 用户在浏览器点「提交订单」
2. 浏览器发请求给后端：「我是 mingzhou，帮我下一单即刻设计」
3. 后端验证：密码对吗？积分够吗？牙位选了吗？
4. 后端写数据库：新建一条订单记录，扣掉积分
5. 后端回复浏览器：「下单成功，单号 MY-260805-001」

## 二、文件逐个讲解

### 1. `package.json` —— 项目身份证

```json
{
  "dependencies": {
    "express": "^4.21.2"
  }
}
```

**干嘛的：** 告诉 Node.js 这个项目需要哪些外部工具包。这里只需要 `express` 一个——它是一个"帮你接电话"的工具。

**类比：** 你开了一家店，express 就是前台接线员。别人打电话过来，express 负责接听，然后转给对应的同事（也就是下面的 routes.js）。

**关键字段：**
- `"type": "module"`：告诉 Node.js 用最新的 `import` 语法（而不是老式的 `require`）
- `scripts`：`npm start` 这个命令会执行 `node src/index.js`

---

### 2. `src/index.js` —— 入口文件，程序的大门

```javascript
const app = express()
app.listen(3001)
```

**干嘛的：** 整个后端的启动点。相当于你按下了电源开关。它做三件事：

**① 开端口**
```
app.listen(3001)   // 在 3001 号端口"接电话"
```
端口就像一个分机号。前端在 3000 端口，后端在 3001 端口。浏览器访问 `http://localhost:3001/api/health` 就能联系到后端。

**② 装插件（中间件）**
```javascript
app.use(express.json({ limit: '100mb' }))  // 允许接收最大 100MB 的数据
app.use(cors)                                // 允许前端跨端口调用
```
`express.json()` 让你能读取浏览器发来的 JSON 数据（比如下单的表单内容）。
CORS 是"跨域"的意思——前端在 :3000 跑，后端在 :3001 跑，浏览器默认不允许它们通信，CORS 就是开个绿灯。

**③ 挂路由**
```javascript
app.use('/api', routes)   // 所有接口都在 /api/ 下面
```
所有业务逻辑都在 `routes.js` 里。这里只是说"地址以 /api/ 开头的请求，都转给 routes 处理"。

④ 健康检查：`/api/health` 返回 `{"ok": true}`，用来测试后端是否活着。

### 3. `src/db.js` —— 数据库管理，数据的仓库管理员

```javascript
const db = new DatabaseSync('data/muye.db')
```

**干嘛的：** 所有跟数据库打交道的事都在这里。

**核心概念：SQLite**

这是一个"轻量级"数据库——不需要安装任何软件，不需要配置，整个数据库就一个文件 `muye.db`。

```sql
-- 就像这样：表格套表格，每张表存一类数据
clients 表：    | id | name | phone | points |
designers 表：  | id | name | phone | group_id |
orders 表：     | id | no | client_id | type | status | points |
```

**这个文件里重要的函数：**

| 函数 | 作用 | 新手怎么理解 |
|------|------|-------------|
| `tx(fn)` | 事务包装 | "原子操作"——要么全做完，要么全不做。比如扣积分：如果扣了积分但订单没创建成功，自动退回来。就像银行转账：不会出现钱扣了但对方没收到。 |
| `nextSeq()` | 生成单号序号 | 每次下单 +1，保证 MY-260805-001、002、003... 不重复 |
| `rowToOrder()` | 字段名转换 | 数据库里用 `client_id`（下划线），前端用 `clientId`（驼峰），这个函数负责转换 |
| `seed()` | 填充初始数据 | 第一次启动时自动创建演示账号（admin/mingzhou 等），第二次启动检测到已有数据就跳过 |

**新手常见疑问：**
- Q：为什么 `INSERT INTO orders (id, no, client_id...)` 括号里那么多字段？
- A：因为一条订单包含的信息太多了——谁下的单、什么类型、几颗牙、什么要求、多少积分、什么时候提交……数据库必须全部记下来。

### 4. `src/auth.js` —— 安全护卫，验证身份

```javascript
const hash = crypto.scryptSync(password, salt, 64)
```

**干嘛的：** 负责三个安全任务：加密密码、验证登录、检查权限。

**① 密码加密（为什么不能存明文？）**

如果你把密码直接存数据库：
```
admin  muye2026   ← 别人攻破数据库就能看到所有密码
```

加密后存数据库：
```
admin  a1b2c3d4...:e5f6g7h8...   ← 即使数据库泄露，别人也解不出密码
```

`scrypt` 是一种"单向加密"——你可以验证密码正确，但无法从密文反推密码。就像碎纸机：你可以把纸塞进去，但没法把碎纸拼回去。

`salt`（盐）是一个随机数，确保即使两个人密码相同，密文也不同。

**② 登录令牌（session）**

登录后，后端生成一个令牌（一串随机字符），存到数据库，并告诉浏览器："以后每次请求都带上这个令牌"。

```
浏览器：我要下单。（附带令牌 abc123）
后端：查一下...令牌 abc123 属于 mingzhou，他是客户，允许下单 ✓
```

令牌 7 天后过期，需要重新登录。改密码后旧令牌立即作废。

**③ 权限检查**

```javascript
requireAuth       // 检查是否登录（有没有令牌）
requireRole('admin')  // 检查是不是管理员
```

这就是为什么设计师不能进管理后台、客户不能改别人订单——这些接口前面都挂了这个锁。

### 5. `src/routes.js` —— 业务核心，所有功能都在这里

**干嘛的：** 这是最长的文件，包含平台的全部业务规则。每一个以 `routes.post('/xxx')` 开头的块就是一个功能。

结构是统一的：
```javascript
routes.post('/api/orders', requireAuth, requireRole('client'), (req, res) => {
    // 1. 检查输入（牙位选了吗？积分够吗？）
    // 2. 做业务逻辑（扣积分、建订单、记录流水）
    // 3. 返回结果（下单成功 / 积分不足）
})
```

**各接口功能速查：**

| 接口路径 | 谁可以调用 | 功能 |
|----------|-----------|------|
| `POST /api/auth/login` | 任何人 | 登录，返回令牌 |
| `POST /api/auth/logout` | 已登录 | 退出 |
| `GET /api/bootstrap` | 已登录 | 获取全部数据（按角色过滤） |
| `POST /api/orders` | 客户 | 提交新订单（扣积分+生成单号） |
| `POST /api/orders/:id/accept` | 设计师 | 抢单（原子锁，仅限待接单） |
| `POST /api/orders/:id/submit-design` | 设计师 | 提交设计文件完成订单（返工重做也走这里，返工次数+1） |
| `POST /api/orders/:id/return` | 设计师 | 退回订单（信息不全） |
| `POST /api/orders/:id/resubmit` | 客户 | 退回订单修改后重新提交 |
| `POST /api/orders/:id/cancel` | 客户 | 撤回订单（退积分） |
| `POST /api/orders/:id/rework-requests` | 客户 | 申请返工（订单立即回原设计师重做，不进大厅） |
| `POST /api/reworks/:id/approve` | 管理员 | 审核通过：登记+退积分（订单留原设计师重做） |
| `POST /api/reworks/:id/reject` | 管理员 | 审核不通过：不退积分（订单仍留原设计师修改） |
| `DELETE /api/reworks/:id` | 客户 | 撤销返工申请（订单恢复已完成） |
| `PATCH /api/reworks/:id` | 客户 | 修改返工申请 |
| `POST /api/notices/read-all` | 客户 | 全部消息标为已读 |
| `POST /api/admin/points` | 管理员 | 充值/扣减积分（扣减不允许扣成负数） |
| `POST /api/admin/accounts` | 管理员 | 创建账号 |
| `POST /api/admin/accounts/:id/reset-password` | 管理员 | 改密码 |
| `DELETE /api/admin/accounts/:id` | 管理员 | 删账号 |
| POST/PATCH/DELETE `/api/admin/groups` | 管理员 | 设计师分组增改 |
| POST/PATCH/DELETE `/api/admin/client-groups` | 管理员 | 客户分组增改删 |
| POST/DELETE `/api/admin/assignments` | 管理员 | 分组匹配规则 |
| `POST /api/admin/design-params` | 管理员 | 保存设计参数 |
| `POST /api/admin/orders/:id/dispatch` | 管理员 | 重新派发未分配订单 |

**几个关键概念：**

- **`:id`**：路径里的冒号是"占位符"。`/api/orders/o-001/accept` 和 `/api/orders/o-003/accept` 走同一个函数，函数里通过 `req.params.id` 取到具体的订单号。

- **`tx(() => { ... })`**：事务。积分操作的函数里都包了一层这个，保证"扣积分"和"建订单"要么同时成功、要么同时失败。

- **`applyRouting()`**：下单后检查客户组有没有匹配的设计师组。没有就自动变成"未分配"状态。

- **抢单锁**：
  ```sql
  UPDATE orders SET designer_id = ?, status = 'designing'
  WHERE id = ? AND status = 'pending'
  ```
  两个设计师同时点接单，SQL 会保证只有一个人能成功。第二个人执行这条 SQL 时 `changes === 0`，后端返回"手慢了"。注意只有「待接单」状态的订单能抢——返工重做的订单留在原设计师手上，不进大厅、不可被抢。

### 6. `src/schema.sql` —— 数据库设计图

**干嘛的：** 建表的 SQL 语句。就像盖房子前画的图纸——定义了数据库里有哪些表、每个表有哪些列、每列是什么类型。

**12+1 张表速览：**（12 张业务表 + 1 张 `meta` 系统元数据表，存放种子标记与单号序号）

| 表名 | 存什么 | 关键字段 |
|------|--------|---------|
| `clients` | 医院/加工厂 | name, phone, points, client_group_id |
| `designers` | 设计师 | name, phone, id_card, group_id |
| `groups` | 设计师分组 | name, leader_id, note |
| `client_groups` | 客户分组 | name, note |
| `assignments` | 匹配规则 | client_group_id ↔ designer_group_id |
| `orders` | 订单 | no, client_id, designer_id, type, teeth, status, points |
| `point_txns` | 积分流水 | client_id, delta, balance, reason |
| `notices` | 消息通知 | client_id, text, is_read |
| `rework_requests` | 返工申请 | order_id, reason, status |
| `accounts` | 账号 | username, pass_hash（加密后的密码） |
| `sessions` | 登录令牌 | token, account_id, expires_at |
| `design_params` | 设计参数 | inner_crown, occlusal_cut, proximal_cut |

**新手怎么理解表关系：**

```
一个客户(client)  ──下──→  多张订单(order)
一张订单(order)   ──被接──→  一个设计师(designer)
一个设计师(designer) ──属于──→  一个分组(group)
一次下单          ──产生──→  一条积分流水(point_txn)
一张完成的订单     ──可申请──→  一条返工(rework_request)
```

### 7. `data/muye.db` —— 数据库文件

**干嘛的：** 这就是数据库本身。所有数据都存在这一个文件里。

- 第一次启动后端时会**自动创建**（不需要手动建库）
- 删除这个文件 = 清空所有数据（相当于"恢复出厂设置"）
- 备份 = 把这个文件复制一份存到别的机器上

旁边两个文件 `muye.db-shm` 和 `muye.db-wal` 是 SQLite 的工作文件，不用管。

## 三、新手常见问题

**Q1：前端和后端的区别是什么？**

前端 = 在浏览器里跑，负责画界面（按钮、表格、弹窗）
后端 = 在服务器上跑，负责存数据、算积分、验证身份
它们通过 HTTP 请求通信（你点"登录"→前端发请求→后端验证密码→返回结果→前端显示页面）

**Q2：为什么需要后端？演示版不是直接用 localStorage 的吗？**

localStorage 是存在你自己电脑的浏览器里的。别人看不到你的数据，你也看不到别人的。正式上线后，一个医院下的单，设计师必须能看到——这就需要一个"大家都访问的中间数据库"，也就是后端。

**Q3：SQLite 够用吗？需要 MySQL 吗？**

几十家医院、每天几百单，SQLite 完全够用。没有任何安装配置，备份就复制一个文件。等业务大到每天上千单时，表结构是标准的 SQL，可以无缝迁移到 MySQL。

**Q4：这个表格里的 `id` 是什么？为什么要一串随机字母？**

`id` 是每条记录的唯一标识符，就像身份证号。用随机字符串（如 `o-m3x2k8j1`）而不是自增数字（1,2,3...），是因为：
- 不会有两个人同时下单拿到同一个 id（即使换到 MySQL 也一样）
- 安全：别人无法通过猜数字来遍历你的订单

**Q5：积分扣减为什么不直接在客户端做？**

因为不安全。F12 打开浏览器控制台，一行代码就能改 localStorage。积分=钱，必须由后端来控制。所有涉及积分的操作都在 `tx()` 事务里完成，保证几个操作同时成功或同时失败。

## 四、本地如何启动

